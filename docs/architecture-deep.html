Plate 01 · Runtime topology

Two computers, one HTTPS seam

The browser owns the setlist and the interaction. A single Cloud Function owns every network operation that needs a secret, an allow-list, or Firestore Admin rights. Firebase Hosting is the only edge between them in normal use.

What to notice

  • Hosting serves the built SPA and rewrites /api/** to the function. In production, sheet extraction takes the direct function URL because Hosting cuts rewritten requests at 60 seconds.
  • The function is the only holder of GEMINI_API_KEY and the only holder of Firestore Admin credentials.
  • The browser can still do useful work offline: the setlist, cached songs and preferences are local. Only new imports, search, publishing and refreshing a share need the network.

Scope

Firebase Analytics is intentionally omitted from this plate; it is a browser-side telemetry dependency, not part of the request path. Google Analytics loads only in production and is disabled by the privacy toggle.

Plate 02 · Frontend layers

The browser is a layered local application

The frontend is not a thin form over an API. It owns a data model, a set of domain transforms, and a persistence layer. The layers below are ordered by dependency: each upper band calls the bands beneath it, while the bottom band is the only place that knows a server exists.

What to notice

  • SessionPage is the frontend's orchestration hub: it loads the setlist and cached songs, retries failures, applies key changes and simplification, edits sections and chords, drives the ambient pad, and builds share payloads.
  • songCache is keyed by a normalized URL. It keeps successful songs, redirect aliases, and a 60-second failure marker so a retry does not immediately re-hit a blocked source.
  • There is no global state library. React state lives in the pages; durable state lives in IndexedDB and localStorage; cross-page services are module singletons.

The coupling that matters

The frontend imports real backend modules, not copies: types/song.ts re-exports functions/src/types; chords.ts re-exports the backend chord helpers; setlistImport imports splitUrls/validateUrls; searchResults imports the backend result selector.

That keeps contracts aligned but couples the frontend build to backend source. Any refactor of those modules is a two-sided change.

Plate 03 · Backend modules

One function, four pipelines, three shared dependencies

Inside the api function, path dispatch is the only router. Four pipelines hang off it, and they converge on source access, song shaping, and Firestore. The graph is ranked by dependency: arrows point from a module to what it relies on.

What to notice

  • scrapePool uses two workers, a per-host gate, and a circuit breaker. Three 403/429 responses from one host pause it for ten minutes. The chart cache is checked before any outbound fetch.
  • searchCache is an instance-local LRU with a Firestore mirror. Complete results persist for five minutes; partial results persist for thirty seconds and stay in memory only.
  • sharedLyricsStore writes the root and song documents in a transaction with a shared rev; reads retry up to three times if a concurrent publish is detected. shareStore uses a batch write for immutable set snapshots.

Cross-cutting code

metrics.ts records timings for chart fetch, parse, cache lookup, search site and search total. It is deliberately not a node here: nothing depends on it, and it never changes a response.

The router calls guards before doing work, not in middleware: every route family validates its own body shape, then checks the IP limit. That keeps the error codes specific (BAD_REQUEST, RATE_LIMITED, INVALID_URL).

Plate 04 · Cold import sequence

What one pasted link actually does

This is the happy path with a cold cache. The optional frame is the expensive branch: only a cache miss reaches the network. Every successful chart is written back before the browser gets the response.

What to notice

  • The cache lookup happens before any outbound request. Identical concurrent loads are coalesced in memory, so two requests in one instance share the same promise.
  • The scrape path is one continuously filled worker queue, not fixed pairs. A slow host does not idle the other worker; a per-host gate caps simultaneous work at two.
  • The browser never sees an unvalidated URL. checkUrl runs before the cache and again inside safeFetch, which also resolves DNS and rejects private or reserved IPs.

Failure shape

A cache miss that fails does not write a chart entry. The route returns an error item in results while keeping the rest of a batch valid. On the client, songCache records a 60-second failure marker so an immediate retry does not re-hit the source.

If the request is served from cache, the entire optional frame is skipped and the response returns immediately.

Plate 05 · Sheet extraction

Deterministic first, Gemini only when needed

Uploaded PDFs are split into one-page files on the client. On the server, every PDF page gets a text-layer analysis before any model call. Pages with usable text take the deterministic SongSelect route; only scanned, image-only or low-confidence pages become Gemini vision batches.

What to notice

  • The client uses pdf-lib to explode a PDF into one-page PDFs, and canvas-resizes images to a 1600px maximum at JPEG quality 0.85 before base64 upload.
  • Page classification is evidence-based: meaningful character count, printable ratio, text-item count, and whether the page paints images. Garbled text is classified uncertain and falls back.
  • Only fallback pages need a Gemini key. A request with a digital PDF and no key can still succeed; a request with a scanned page fails with a specific message naming the page and reason.

The retry rule

Vision pages are chunked into ordered batches. Each batch asks for every section and preserves chord alignment. Songs that continue across pages are merged by original title.

If the caller supplied expectedSongCount and the first pass is short, the whole vision pass runs once more with a completeness instruction. If the retry still disagrees, the request fails with ExpectedSongCountMismatchError instead of silently returning the wrong set.

Plate 06 · Data & sharing

Firestore is a server-owned store with two publication shapes

Set links are immutable snapshots written in one batch. Lyrics links are mutable publications written in a transaction, keyed by a secret-derived ID and guarded by a revision. Three cache collections live beside them and share the same Admin-only access rule.

What to notice

  • sharedSets is immutable: one batch writes the root plus one document per song. The snapshot format is versioned (v: 2) and carries the full per-set choices, not just the source song.
  • sharedLyrics is mutable: publishing rewrites the root and song documents in a transaction, increments rev, deletes stale song documents when the set shrinks, and resets the seven-day expiry.
  • The lyrics document ID is not random. It is SHA-256 of lyrics-share-v1: plus a 32-byte browser secret, so the server can verify the bearer secret without storing a separate mapping.

Cache lifetimes

sourceCharts live six hours, chartAliases 24 hours, complete search results five minutes, and partial search results thirty seconds in memory only. Failed charts are never written as valid cache entries.

Firestore security rules deny every client read and write on every path. The Admin SDK inside the function is the only writer. TTL policies on expiresAt for the two share collections handle physical cleanup after the server-side expiry check.

Plate 07 · Build & release

A commit crosses two compilers before it becomes production

The frontend and the functions package build separately. GitHub Actions is the only deployer: it runs lint, tests and both builds, then deploys Hosting, Functions and Firestore rules with the same service account.

What to notice

  • The root build is tsc -b && vite build; the functions package has its own TypeScript build to lib/. Both must pass before deploy.
  • Vite proxies /api to the Functions emulator at 127.0.0.1:5001/demo-chords/us-central1/api in development. Production uses the Hosting rewrite.
  • Deployment is one Firebase command for Hosting, Functions and Firestore rules. The service account needs permissions for all three, even when only one changed.

Secrets and environments

Browser config comes from VITE_FIREBASE_* and is public by design. The Gemini key is a Functions secret. Firestore rules are deployed with the code, so a rules regression is a deploy-time event, not a dashboard-only change.

Local sharing is not a complete stack: the Functions emulator alone does not provide Firestore. Use the Firebase Firestore emulator and Admin SDK wiring for isolated sharing work.

Plate 08 · Search stream

Search answers before all three sites do

This is the cold-cache path. The function starts all three source searches at once, writes an NDJSON source event as each one settles, then writes the final balanced selection. On a cache hit, the whole fan-out is skipped and the complete payload returns after the lookup.

What to notice

  • All three searches start together. Each settled source calls onOutcome, and the route writes a source event immediately; the browser can render cards before the slowest site finishes.
  • Complete results are cached for five minutes in memory and Firestore. Partial results are cached for thirty seconds in memory only. In-flight de-duplication is per instance, not a distributed lock.
  • The final selector keeps Ultimate Guitar's native order up to three results, then balances the remaining slots across the other sources by relevance and source-local rating.

Failure shape

Each source outcome is typed ok, empty or failed with a reason of timeout, blocked, fetch or parser. One failed source never hides another; the complete event carries all source statuses and a partial flag.

On the client, partial candidates reserve capacity per source so a fast Ultimate Guitar response cannot fill all eight result slots before the other sites answer.

01

One network entry. Every /api/** call dispatches inside the single api function. Production sheet extraction is the only deliberate bypass of the Hosting rewrite.

02

Validate before fetch. checkUrl and safeFetch enforce HTTPS, the four-domain allow-list, DNS/IP checks, timeouts and response-size limits.

03

Deterministic first. A PDF page with a usable text layer goes through the SongSelect parser. Gemini handles only scanned, image-only or low-confidence pages.

04

Local-first. Setlists, source songs, aliases and display preferences are browser-owned. Firestore holds shared publications and disposable caches, not the user's library.

05

Admin-only store. Firestore rules deny every browser read and write. Only the function's Admin SDK credentials can touch the collections.

06

Two publication semantics. Set links are immutable batch snapshots. Lyrics links are mutable transactions with a shared rev and a secret-derived ID.

07

Bounded work. Two scrape workers, two requests per host, three function instances, concurrency five, 20 URLs, 10 files, 15 songs.

08

Errors are data. Batch scrapes return per-item outcomes, search streams carry source statuses, and extraction streams progress before it streams a result or an error.
